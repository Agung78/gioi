## 🔴 High

### 1. `/admin/analytics` loads unbounded rows and aggregates in JS
- `guest.findMany({ where: { venueId } })`: every guest in the venue, including phone, allergies, notes. No LIMIT.
- `feedback.findMany({ where: { venueId } })`: every feedback row. No LIMIT.
- `reservation.findMany` with `include: { guest: true }`: full guest row per reservation, range + 30 days.
- All counts and rates are computed in JS.

Effect: response size grows with the guest list. Personal data the page never shows is sent to the browser.

Fix (query-patterns: LIMIT, select only needed columns, aggregate in the database):
- Compute counts and rates in SQL (`GROUP BY`, `count(*) FILTER (WHERE ...)`) and return totals only.
- Return the feedback list with `LIMIT` and keyset pagination on `(submitted_at DESC, id DESC)`.
- Select only the guest fields the dashboard renders.

## 🟡 Medium

### 2. FK columns without an index
```sql
CREATE INDEX reservations_created_by_id_idx ON reservations(created_by_id);
CREATE INDEX reservations_updated_by_id_idx ON reservations(updated_by_id);
CREATE INDEX reservation_status_events_actor_user_id_idx ON reservation_status_events(actor_user_id);
```
Users are deactivated (`active`), not deleted, so the cost today is small. Add these before any staff-activity stats are added.

### 3. Double table booking is not enforced by the database
`reservation_tables` comment: "a table can be held by one reservation at a time". The PK `(reservation_id, table_id)` does not enforce this over time. Only `src/lib/tables.ts` does.
DB-level fix: store a time range on `reservation_tables`, then add an exclusion constraint:
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE reservation_tables
  ADD CONSTRAINT reservation_tables_no_overlap
  EXCLUDE USING gist (table_id WITH =, held_during WITH &&);
```
Cancelled and no-show reservations must release the range, either through a partial constraint (`WHERE`) or by clearing the range.

### 4. Missing `created_at`
`reservation_tables` has no record of when a table was assigned. That timestamp is needed for table-utilisation analytics.
Also missing on: `opening_hours`, `closed_dates`, `floor_tables`, `floor_objects`.
```sql
ALTER TABLE reservation_tables ADD COLUMN created_at timestamptz NOT NULL DEFAULT now();
```

## 🟢 Low / Defer

### 5. Enums vs CHECK
`reservation_status`, `reservation_channel`, `venue_role` and `actor_type` are Postgres ENUM types. The skill prefers CHECK constraints. `ALTER TYPE ... ADD VALUE` is cheap; removing a value is not. No migration needed.

### 6. Explicit `onDelete`
`Reservation`, `Guest`, `Feedback` and `ReservationStatusEvent` relations use the default (block the delete). That is the right behaviour for history. State it explicitly with `onDelete: Restrict` so the intent is clear.

### 7. Partial / covering indexes
Do not add any yet. Confirm with `EXPLAIN ANALYZE` after item 1 changes the query shape.

## 📊 Intelligence for `/admin`

The dashboard currently shows: today live, next 7/30 days, guest mix, channels, reliability, action cues, feedback list.

### From `reservation_status_events` (written on every status change, never read by the dashboard)
| Panel | Derivation | Why |
|------|------------|-----|
| Real table turn time | `seated` → `completed` duration, by area and party size, compared with `venues.dining_minutes` | Checks whether the 120 min setting is right; that setting determines how many tables can be sold |
| Punctuality | `arrived` event `at` − `reservations.starts_at`; late rate against `grace_minutes`, by channel | Shows how often guests arrive late |
| Cancellation timing | `cancelled` event `at` vs `starts_at` (hours before), compared with the cancellation policy | Shows how many cancellations come too late to resell the table |
| Confirmation lag | `pending` → `confirmed`, per channel | Shows how quickly staff confirm bookings |

### From reservations and guests
| Panel | Derivation |
|------|------------|
| No-show risk | No-show rate by channel, by lead-time bucket (`starts_at − created_at`), by party size, first-time vs repeat; list of guests with 2+ no-shows |
| Lapsed regulars | Guests with 3+ visits and last visit over 60 days ago; filter on `marketing_consent` for outreach |
| Demand heatmap | Covers by weekday × time slot, against `seating_areas.capacity` |
| Lead-time spread | Lead-time distribution per channel (today: one overall average) |
| Kitchen prep | Allergies among covers booked for today and the next 7 days |

### From feedback
- Response rate: feedback ÷ completed reservations.
- Rating trend over time.
- Service tags ranked by how often they come with low ratings.
- Rating by seating area, channel, occasion.

### Tables and staff
- Table utilisation: `reservation_tables` ⋈ `floor_tables`; idle tables (needs item 4).
- Staff activity: bookings created or changed and status changes per user (`created_by_id`, `updated_by_id`, status events, `audit_events`) (needs item 2).

### Not possible yet
Revenue and spend per cover. Spend is not stored. Needs a new column or a POS integration.
